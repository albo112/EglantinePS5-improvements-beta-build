## Ordinary texture refusal ownership and retry contract

The only non-null `Vulkan::Image` constructor callers are normal `JoinImages` insertion and `ReplaceColorFeedbackViews` shadow insertion. The null image constructor and move into pending downloads do not enter this path.

The PS5 build generates `common/slot_vector.h` through `headless/slot_vector_recovery.cmake`: `insert` is allowed to throw, restores the popped free-list index in its catch block, and sets the stored bit only after successful construction. The ordinary rejected constructor path has not initialized sparse tile/layer resources, registered image/image-view/descriptor entries, or scheduled GPU work. Its `vk::Image` member is a complete object, so constructor unwinding calls its destructor and `vmaDestroyImage` for the unused empty VkImage. Base/vector members also unwind normally.

Overlay 0432 moves the existing normal insertion refusal block into `TextureCache::TryMakeImage`; normal `JoinImages` and feedback shadows share its existing one-second size-aware pause. There is no new memory cap or allocator fallback removal. A refused shadow binds `NULL_IMAGE_VIEW_ID` for that use and is retried on later draws. Null slot zero is created at texture-cache startup; Vulkan's null image view uses supported null descriptors or the existing fallback image. A successful shadow is added to the shadow cache only after successful construction. It never samples a target while that draw writes the target merely because the new shadow ran out of memory.

Normal descriptor failures already avoid caching a null view: `VisitImageView` removes the refused descriptor entry, and `TickFrame` invalidates image tables when the refusal pause expires. `InsertImage` returns before publishing into the allocation table when `JoinImages` refuses. On recovery, normal creation reloads guest data without requiring another guest write. Writes made to a refused render target during an actual memory shortage can still be lost, as documented by the existing refusal policy. Explicit end-on-OOM configuration and exceptions other than device OOM still propagate.

## Cached classification investigation and reversible test

The live `GenericEnvironment::IsCbufStorageBufferPointer` inserts every computed direct classification into `storage_pointer_types` (`shader_environment.cpp:207–217`). The indirect variant records its tagged key as well (:224–240). `GenericEnvironment::Serialize` writes the map count and every u64-key/u8-value pair (:303,311–312,336–339). `FileEnvironment::Deserialize` reads that count and the same pair widths (:876,883–884,917–923). The replay lookup then throws if the requested key is absent (:966–970). No obvious omitted map serialization or pair-width mismatch was found by this source audit. This is not a serialization round-trip test with actual game shader records.

The Vulkan cache format is version 23; supplied overlay 0200 bumped it from 22 to 23 when indirect storage-pointer tracking changed. The format header can reject a different version, but does not record every translation flag/profile setting or prove complete metadata. The PS5 frontend replaces `LoadPipelines` with `headless/shader_cache_reader.inc`, which validates/repairs incomplete cache tails; it still invokes the same `FileEnvironment::Deserialize`. It does not supply classifications missing from a complete record. These shader compilation exceptions are caught by pipeline creation; they do not establish a truncated-file event. No cache-repair, invalid-header or old-version-deletion diagnostic was found in the supplied logs.

Logs5/205143 loads the driver pipeline cache at 19.116622s (line 1633), then emits the first cached compute classification failure at 19.266494s (line 1785) and graphics failures from 19.728065s (line 1977). The listed classification failures are in early cache replay, well before the later gameplay mesh draw evidence. The archive contains no actual `vulkan*.bin` shader cache files or producer metadata. Therefore the proven condition is a replay request for an unrecorded classification key; stale same-version records, changed translation/settings paths and incomplete live recording remain competing explanations. Test4-A adds no arbitrary replacement classification and does not claim to fix this separate defect.

The PS5 paths are derived from `storage_paths.h`, the generated PS5 `path_util.cpp` branch, and `PipelineCache::LoadDiskResources`:

1. Quit the game and emulator cleanly. Copy `/data/eglantineps5/user/cache/shader/0400486024dec000/` to the PC, preserving all four possible files: `vulkan.bin`, `vulkan_mesh.bin`, `vulkan_used.bin`, `vulkan_pipelines.bin`.
2. Rename that title folder on the console to `0400486024dec000-Test3-backup`; do not delete it. Leave saves, keys, firmware, game files and configuration intact.
3. Run Test4-A through the same scene and collect logs. Exit cleanly so cache writes finish. Run again through that scene without changing settings and collect warm-run logs.
4. If the cold run succeeds but the newly written warm cache reproduces classification failures, investigate current recording/replay. If clean cold and warm runs work but restoring the original folder brings back failures, stale/incomplete original records are strongly supported. Preserve both cache versions and logs for exact-key comparison.
5. A separately labelled fully cold driver-cache trial also backs up/renames `/data/eglantineps5/cache/radv`; it is not required merely to isolate `FileEnvironment` metadata. Expect extra compilation and potentially higher initial memory pressure in a cold run.

## Arena retention audit — intentionally unchanged

`headless/heap_arenas.inc:256` treats `EDEN_HEAP_KEEP_ARENAS` as a presence flag. Supplied profiles set it to `1`; both periodic return and thread-exit return skip under this policy. The safe existing return algorithm only transfers completely empty non-current arenas to a reusable spare list while holding the arena creation lock. It does not return the physical direct-memory chunk to the OS. The SDK lacks the required mspace-destruction operation; freeing backing memory underneath an mspace is unsafe.

Logs3 `crash-20261107-201432-stderr.log:1746–1751` contains 19 empty compiler arenas (roughly 38MiB of their arena capacity) and about 100MiB of internal room across four compiler records. Existing cross-thread arena adoption is active even with retention enabled. These facts motivate a future measured reuse experiment, but do not prove that flipping this flag would eliminate the pressure seen here. The policy was not changed, no cross-thread live allocation was freed, and no memory ceiling was raised.

## Performance evidence

`graphics-memory-audit.json` extracts actual `EDEN` frame-presentation interval samples, not the nominal 60Hz output clock. Logs3 sessions show medians from 12.810 to 59.366 FPS; Logs4/203446 median 11.784 FPS, Logs4/203836 median 32.6385 FPS; Logs5/205143 median 1.100 FPS with very heavy debug logging and intervals as slow as 0.040 FPS. These are mixed startup/gameplay intervals from unmatched sessions, not controlled performance benchmarks. They confirm that a 60Hz output clock is insufficient evidence for 60FPS gameplay.

The public release's 15–19 FPS and Test3's 30–58 FPS are user observations, not measured here with a common scene. The presence bug proves that some Test3 draws were omitted even with the intended `0` profile, so the observed speedup cannot be attributed entirely to correct rendering improvements. Test4-A retains existing speed work but restores eligible task/mesh draw attempts. New PS5 measurements must report both restored visuals and frame time; no FPS improvement or crash-free duration is claimed from these host tests.
