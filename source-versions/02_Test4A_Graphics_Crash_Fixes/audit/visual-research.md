* **a51a69fb is already ported**, in `0247-flash-02-pr715-paired-pointers.patch`. It enables the paired/loaded search with `EDEN_NX2_PAIRED_POINTERS=1` and retains this port's candidate budgets, with an extra check before binding the paired buffer. Both shipped profiles in `RELEASE-NOTES.md` set that switch to 1. Do not port it twice.
* Both T49 profiles set **`EDEN_NX2_NATIVE_TABLES=1`**, not the user's old `compute`. Source `0202` makes 1 the all-stage mode; `0248` adds a separate compute+mesh mode. All-stage tables remove an explicit graphics-pointer restriction. `0201` separately raises the bound region for read-only table pointers, with the shipped 128 MiB cap. Its broad `EDEN_NX2_NATIVE_GRAPHICS_SIZE` switch is not in those profiles and is not automatically needed.
* **The 0425 backend float-depth defense is missing.** Overlay `0109-t39-depth-compare-texture-descriptors-stay-float.patch` sanitizes sampled texture descriptors in `texture_pass.cpp`; `0226-t39-amd-01-pr273.patch` assumes that part already handled. No overlay changes `ImageType` to prioritize depth. A direct read of core 0ca2032 confirms `const Id type{desc.is_integer ? ctx.U32[1] : ctx.F32[1]};` in `ImageType`. These are different defense points. Preserve the already-used tiny 0425 backend change (`desc.is_depth ? F32 : desc.is_integer ? U32 : F32`) on the newer target. This is correctness hardening for any path that still constructs depth+integer metadata and a known crash protection, not an exposure correction by itself. [Core source](https://github.com/Djihads80/Eglantine/blob/0ca2032bffc5f1a3fca75427f7d4a4718adda660/src/shader_recompiler/backend/spirv/spirv_emit_context.cpp#L33)
* T49 has a coherent PS5 **driver mesh-as-compute** path and lone-mesh support, which the recomp does not. Both profiles set `EDEN_NX2_RADV_MESH_COMPUTE=1`; only Prettier adds `EDEN_NX2_RADV_MESH_COMPUTE_LONE=1` (the leaf/plant path). Neither shipped profile lists `EDEN_NX2_NO_MESH=1`. Leaving the old NO_MESH switch in the user's env would continue to suppress the feature being adopted.
* The local T49 developer report describes reduced white flashes with `EDEN_NX2_ZPASS_PAUSE=1`, and a second gated query-lifetime fix in Prettier. It explicitly says the trials used different routes, were short, and cold launch/long stability remained unproven. Treat those as author observations, not independent validation from this research. The report also separates persistent dark one-frame glitches from white flashes and table mode.

Recommended implementation conclusion for **T49**: use its existing paired-pointer/all-stage-table/mesh mechanisms in their intended profile, preserve the missing backend float-depth guard as a narrow extra, and verify memory and actual output on PS5. No additional broad Vulkan module transplant is supported by the evidence here. No edits to the supplied T49 source were made.

Precision for the carried 0425 comment: `OpTypeImage` names the flag **Depth**, not Dref. The invalid module in this case has an unsigned sampled type but a float result on `OpImageSampleDref*`; SPIR-V requires the sampled and result types to match. The patch's inherited claim that the general spec universally requires float whenever Depth=1 is too broad. Keep the actual backend repair but describe the concrete emitted type mismatch. [Matching RADV crash/validation report](https://github.com/zortos293/Lichii/issues/236), [SPIR-V specification](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html)

## New candidate: paired and loaded pointer alternatives

[Eglantine a51a69fb](https://github.com/Djihads80/Eglantine/commit/a51a69fbfb97d039b432817a489272cb53732967) changes only `src/shader_recompiler/ir_opt/global_memory_to_storage_buffer_pass.cpp`. The old condition skips candidate search whenever `storage_buffer` is already set. The patch runs the search for paired accesses too; when a pointer loaded from memory competes with the pair, it binds both sources and leaves the backend to select the correct buffer at runtime. When no loaded pointer competes, it retains the existing pair.

The commit identifies near-leaf compute `539ffb3f650a34ac`: foliage placement may use `c0[12]` or `*c0[12]`. Rebasing the loaded path onto the paired buffer reads zero records, normalizes a zero vector, and produces NaN leaf positions. This is a precise missing-foliage mechanism, not a direct gamma adjustment or a proven explanation for every bright scene.

Local evidence: `work/t34-source/tools/eglantine-patches/0170-native-storage-buffer-pointer-tracking.patch` adds the earlier paired/loaded-pointer tracking but still contains `if (native && !storage_buffer && !low_addr.IsImmediate())`. No `paired_found` or `has_loaded_pointer` equivalent appeared in the inspected patch series. `0424-white-02-native-tables-compute-only.patch` leaves these indirect candidates enabled for compute programs but suppresses graphics ones. Thus a51a69fb can affect near-leaf compute with the current compute-only mode, while it cannot compensate for graphics tables explicitly disabled by that mode.

Practical limit: user runs `EDEN_NX2_NO_MESH=1`, so any recovered leaves that need mesh drawing may still remain invisible. The candidate can increase storage bindings; retain the PS5 binding/memory limits and evaluate a matched scene before claiming a visual or performance win.

## Brightness/color-space interpretation

[Lichii #101](https://github.com/zortos293/Lichii/issues/101) separates bloom amplification, a half-resolution water-like layer, missing vegetation, and invalid/dynamic texture handles. Its old shader-reject workaround removes real bloom and river rendering; reports disagree by scene/GPU and later public builds improve without rejection. These shader hashes should only identify a pass in a diagnostic A/B, not become an unconditional brightness fix.

The recomp's UNORM storage view does **not** itself perform an sRGB output encode. A sampled sRGB view performs sRGB-to-linear decode; view/attachment choices must match what the guest shader already wrote. An extra encode can wash out a frame, while a missing encode can darken it. Audit the actual final texture/view, shader math and presentation conversion before changing gamma. Khronos documents the [sRGB decode](https://docs.vulkan.org/spec/latest/chapters/images.html), [extended-usage rules](https://docs.vulkan.org/refpages/latest/refpages/source/VkImageCreateFlagBits.html), and [storage format matching](https://docs.vulkan.org/guide/latest/storage_image_and_texel_buffers.html). No source inspected establishes a universal gamma-slider cure for this Zelda build.

## Conflicting reports and rejected certainty

[Lichii #183 comment 6674126577](https://github.com/zortos293/Lichii/issues/183#issuecomment-6674126577) reports a large improvement on an NVIDIA/Linux build versus `8390649c0c`, but explicitly has no responsible-commit bisect. [A later #101 report](https://github.com/zortos293/Lichii/issues/101#issuecomment-6684238003) on clean `55532f2d814215aaf32a76c214cf129f2cb6282b` still shows outdoor white/yellow washout despite much better vegetation. Neither proves current PS5 behavior.

[Lichii #204](https://github.com/zortos293/Lichii/pull/204) proposed flushing query results on the owning GPU thread before macro DMA reads; it is **closed and unmerged** in the connector result. Its tests were builds/unit tests and its gameplay checks were proposed, so the issue comment declaring the vegetation root cause proven overstates the evidence. The PS5 already has separate query-DMA trace/sync patches (`0317`, `0399`, `0409`) with different gates. Inspect the user's actual sync settings and pending-report traces before changing waits.

Finally, invalid TIC `format=100` or zero-format assertions do not alone prove an unsupported texture format. A wrong dynamic handle can select garbage descriptor words. Validate the raw handle, TIC index/limit, mapped descriptor address and words before adding a guessed format mapping. [Source diagnostic discussion](https://github.com/zortos293/Lichii/issues/183#issuecomment-6672989854)
